# 認証機能の実装手法と内部処理フローのまとめ

このドキュメントでは、本チュートリアルプロジェクトにおいて実装されたユーザー認証機能（仮登録・本登録・ログイン・ログアウト）について、新しく作成・追記したコードの役割や、認証の背後でどのような処理が行われているのかを詳しくまとめています。後から見返せるリファレンスとして活用してください。

---

## 1. 新たに作成・追記した主なファイルと役割

### 📌 APIルートの定義
*   **ファイル**: `routes/api.php`
*   **追加された役割**:
    *   `POST /register/pre`: 仮登録（メールアドレス送信とトークン発行）用エンドポイント
    *   `POST /users`: 本登録（ユーザー情報登録とトークン検証）用エンドポイント
    *   `POST /login`: ログイン用エンドポイント
    *   `POST /logout`: ログアウト用エンドポイント（認証必須）
    *   **ルート保護 (`middleware('auth:sanctum')`)**: コメントの「投稿・更新・削除」や「ログアウト」などのエンドポイントをこのミドルウェアグループで囲むことで、未ログインユーザーからのアクセスを遮断しています。

### 📌 コントローラー (APIリクエストの受付・処理)
APIエンドポイントに対応する具体的な処理プロセスです。

1.  **`EmailVerificationController.php` (仮登録)**
    *   **役割**: `StoreEmailVerificationRequest` でバリデーションされたメールアドレスを受け取り、6桁のランダムなトークンを生成します。これをDB(`email_verifications` テーブル)に有効期限付きで保存し、指定されたメールアドレス宛にMailableクラスを利用してメール送信を行います。

2.  **`UserController.php` (本登録)**
    *   **役割（変更点）**: 元々は単にユーザー情報をそのままDBに登録していましたが、「本登録」の仕組みに変更しました。仮登録で送られたトークンとメールアドレスの照合を `email_verifications` テーブルで行い、有効期限内かつ正しい場合のみ、ユーザー情報を `users` テーブルに保存します。（保存後、仮登録テーブルからレコードを削除します）

3.  **`AuthController.php` (ログイン・ログアウト)**
    *   **役割**: 新設されたコントローラーで、Laravelの組み込み認証機能（`Auth` ファサード）を利用してセッションベースの認証を実現しています。
    *   `login()`: `Auth::attempt` を使用して入力されたメール・パスワードの組み合わせを検証し、正しければセッションを再生成してログイン状態を確立します。
    *   `logout()`: `Auth::logout()` とセッションの破棄 (`invalidate`, `regenerateToken`) を行い、ログイン状態を解除します。

4.  **`CommentController.php` (認証情報の利用)**
    *   **役割（変更点）**: これまではリクエストパラメータから直接 `user_id` を受け取っていましたが、セキュリティリスク（他人のIDを騙れる）を排除するため、`$request->user()->id` を使用して「**現在本当にログインしているユーザーのID**」をサーバー側で取得し、書き込みや所有権（更新・削除）のチェックを行うように修正しました。

### 📌 フォームリクエスト (バリデーション)
リクエストがコントローラーに到達する前に、データが正しい形式かどうかを検証します。

1.  **`StoreEmailVerificationRequest.php` (新規)**
    *   仮登録用のメールアドレスに対して、「必須、メール形式、255文字以内、未登録（`unique:users,email`）」の検証を行います。
2.  **`StoreUserRequest.php` (変更)**
    *   名前の検証だけでなく、「メールアドレス（未登録）、パスワード（8文字以上）、トークン（6桁）」のルールを追加し、本登録時の不正なデータ入力を防ぎます。
3.  **`LoginRequest.php` (新規)**
    *   ログイン時のメールアドレスとパスワードが必須であることを定義します。
4.  **`StoreCommentRequest.php` 等 (変更)**
    *   クライアントから `user_id` を送る必要がなくなったため、バリデーションルールから `user_id` の項目を削除しました。

### 📌 メール関連のクラス
*   **`EmailVerificationToken.php` (Mailable)**
    *   **役割**: メール送信処理をカプセル化したクラスです。内部でトークン情報を保持し、指定されたBladeテンプレートに変数を渡してメールを構成します。
*   **`verification_token.blade.php` (Blade)**
    *   **役割**: ユーザーに送信される実際のメールのHTMLテンプレートです。

### 📌 モデル
*   **`User.php`**
    *   `Laravel\Sanctum\HasApiTokens` トレイトを追加しました。これにより、必要に応じてAPIアクセストークンを発行・管理できる機能が備わりました（現状はセッションベース認証で動かしていますが、設定や今後の拡張でトークンベース認証にも対応可能になります）。

## 2. 認証処理の内部フロー（ログイン〜ルート保護〜ログアウト）

### A. ログイン (`POST /api/login`) が行われる時
1.  **情報の受け取り**: ユーザーがメールアドレスとパスワードを送信します。
2.  **`Auth::attempt($credentials)` の実行**:
    *   Laravelは内部で `users` テーブルを検索し、一致するメールアドレスを探します。
    *   見つかった場合、データベースに保存されている「ハッシュ化されたパスワード」と、入力された「素のパスワード」を照合（暗号学的な比較）します。
    *   一致すれば `true`、不一致なら `false` を返します。
3.  **セッション確立とセキュリティ確保**:
    *   ログインに成功すると、`$request->session()->regenerate();` が実行されます。
    *   これにより、ログイン前と後でセッションID（ブラウザに付与されるCookieの識別子）が新しくなり、**セッションハイジャック攻撃**（他人にセッションを盗まれて不正アクセスされること）を防ぎます。
4.  **Cookieの発行**:
    *   レスポンスを返す際、Laravelは自動的に「このユーザーはログイン済みである」という情報を含むCookie（デフォルトでは `laravel_session` 等）をブラウザへ送り返します。以降の通信ではブラウザが常にこのCookieを添付します。

### B. 認証必須ルートへのアクセス (`middleware('auth:sanctum')`)
保護されたエンドポイント（例: `POST /api/articles/1/comments`）にリクエストが来た場合の動きです。

1.  **ミドルウェアによるインターセプト**:
    *   コントローラーの処理が始まる前に、`auth:sanctum` ミドルウェアがリクエストをチェックします。（Sanctumは、API用のトークン認証だけでなくSPA向けのステートフルなセッション認証も標準でサポートしています。）
2.  **Cookie/セッションの検証**:
    *   リクエストに含まれるCookieを解析し、サーバーに保存されているセッション情報と一致するか、有効期限内か、どのユーザーのものかを確認します。
3.  **通過 または ブロック**:
    *   認証が確認できれば、コントローラーの処理に進みます。この時、Laravel内部の認証状態がセットされ、`$request->user()` で自身のUserモデルに安全にアクセスできるようになります。
    *   認証情報がない、または無効な場合は、処理をブロックし、`401 Unauthorized` を即座に返却します。

### C. ログアウト (`POST /api/logout`) が行われる時
1.  **`Auth::logout()` の実行**:
    *   現在のログイン状態（セッション内のユーザー情報）をクリアします。
2.  **セッションの完全破棄**:
    *   `$request->session()->invalidate();`: セッション情報を完全に無効化します。
    *   `$request->session()->regenerateToken();`: CSRFトークン（フォームを跨いだ攻撃を防ぐ値）も新しく再生成し、古いトークンが使われないようにします。
3.  これにより、ブラウザが持っていたCookieは再び無効な状態になり、以後保護されたルートにアクセスしても `401 Unauthorized` となります。
